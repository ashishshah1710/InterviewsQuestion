m-cj-1 How does HashMap work internally?

ELI5
Hash the key → pick a bucket → walk a list (or a tree if the list got long).
Interview answer
  • hash → (n-1) & hash for index. Collisions: linked list; Java 8 treeifies at 8 nodes if table ≥ 64.
  • Load factor 0.75 → resize (double). equals+hashCode must match or get() misses.
  • Not thread-safe. Project line: we never share a HashMap across request threads; caches use ConcurrentHashMap or Redis.

m-cj-2 Difference between "==" and equals()

ELI5
== compares the house address. equals() compares what's inside the house.
Interview answer
  • == : same object reference (or unboxed primitives).
  • equals(): value. String/Integer: override it. Default Object.equals is still ==.
  • Integer cache −128..127 can make == look true — never use == for objects in business code.

m-cj-3 Overloading vs Overriding

ELI5
Overloading: same kitchen, different recipes (compile time). Overriding: child rewrites the parent's recipe (runtime).
Interview answer
  • Overload: same name, different params; static binding.
  • Override: same signature in subclass; @Override; runtime dispatch. static/final/private cannot override.
  • Project: we override equals/hashCode on entities carefully; we overload constructors or factory methods, not both in confusing ways.

m-cj-4 Explain SOLID principles

ELI5
Five habits so a class doesn't become a junk drawer.
Interview answer
  • S: one reason to change (PaymentService doesn't send email).
  • O: add a Strategy bean, don't edit a 200-line switch.
  • L: subtype must honor the parent contract.
  • I: small interfaces — don't force extra methods.
  • D: inject interfaces, not concrete UpiClient.

ELI5
map: one box → one box. flatMap: one box → several, then flatten into one stream.

filter keeps or drops. map changes the shape. They do different jobs.
Interview answer

filter(Predicate) — same type, fewer elements. map(Function) — maybe different type, same count (unless later filter). Pipeline: filter first when you can, so map does less work.

m-col-1 ArrayList vs LinkedList

ELI5
ArrayList is numbered seats (jump to #50). LinkedList is a conga line.
Interview answer

Always default ArrayList. LinkedList loses on cache locality; O(1) insert in the middle is a myth unless you already hold the node. Use ArrayDeque if you need a queue.

m-col-2 HashMap vs ConcurrentHashMap

ELI5
HashMap is a notebook for one person. ConcurrentHashMap lets many people write on different pages.
Interview answer

CHM: no nulls, bin-level concurrency, atomic compute/merge. synchronizedMap is one giant lock — don't use it for caches.

m-col-3 HashSet vs TreeSet

ELI5
HashSet is a bag of unique stickers (no order). TreeSet hangs them on a sorted tree.
Interview answer
  • HashSet: O(1) avg, one null, needs hashCode/equals.
  • TreeSet: O(log n), sorted, no null (unless comparator allows), needs Comparable/Comparator consistent with equals.

m-col-4 How does ConcurrentHashMap work?

ELI5
It doesn't lock the whole map. It locks (or CASes) one bin at a time.
Interview answer
  • Reads are usually non-blocking. Writes CAS the bin head; contended bins lock that node.
  • size() is an estimate under concurrency. Iterators are weakly consistent — no CME.
  • Never iterate and structurally mutate a HashMap from many threads; use CHM.computeIfAbsent for caches.

m-mt-1 What is a deadlock?

ELI5
Two people each hold one chopstick and wait for the other forever.
Interview answer
  • Needs: mutex, hold-and-wait, no preemption, circular wait.
  • Detect: jstack / jcmd Thread.print. Prevent: lock order, tryLock timeout, fewer locks.
  • DB deadlocks: Postgres aborts one TX — retry that TX.

m-mt-2 synchronized vs Lock (ReentrantLock)

ELI5
synchronized is the simple door lock. ReentrantLock is the lock with a timeout and a 'try'.
Interview answer
  • synchronized: auto unlock, less code, no tryLock, no fairness knob, one condition (wait/notify).
  • Lock: tryLock, lockInterruptibly, multiple Conditions, must unlock in finally.
  • Project: we used ReentrantLock.tryLock when a request must fail fast instead of waiting forever.

m-mt-3 Runnable vs Callable

ELI5
Runnable is fire-and-forget. Callable returns a result (and can throw).
Interview answer

ExecutorService.execute(Runnable) vs submit(Callable) → Future. Uncaught exceptions in execute can vanish; submit stores them on the Future — you must get().

m-mt-4 What is ExecutorService?

ELI5
A pool of reusable workers plus a queue, instead of new Thread() for every task.
Interview answer
  • submit / invokeAll / shutdown vs shutdownNow.
  • Size: CPU-bound ≈ cores+1; IO-bound larger or virtual threads. Bounded queue + rejection policy.
  • Project: @Async used a named pool, not the default simple executor, so we could see queue depth in metrics.

m-mt-5 CompletableFuture use cases

ELI5
A promise: 'text me when the three downstreams answer.'
Interview answer
  • Fan-out: allOf(user, orders, payments) then join — cut 30s sequential calls.
  • thenCompose for dependent async; exceptionally for fallback cache.
  • Don't join() on a Tomcat thread without timeouts; don't block the common ForkJoinPool with JDBC.

m-sb-1 @Component vs @Service vs @Repository

ELI5
All mean 'this is a Spring bean.' The extra names tell humans and tools the layer.
Interview answer

@Repository also translates SQL exceptions to DataAccessException. @Service is business. Don't stack all three on one class.

m-sb-2 What is Dependency Injection?

ELI5
You don't new the toolbox. Spring hands you the toolbox (constructor).
Interview answer

Constructor injection on a singleton: collaborators are final, easy to test, fail-fast on missing beans. Field @Autowired is harder to test. Project: we inject interfaces (PayClient), never new RestTemplate inside methods.

m-sb-3 @Bean vs @Component

ELI5
@Component: Spring finds your class. @Bean: you write a factory method, usually for 3rd-party types you don't own.
Interview answer

@Configuration + @Bean for RestClient, ObjectMapper, Kafka templates. @Component for your own services. @Bean methods on a plain class are 'lite' — inter-@Bean calls may skip the singleton cache.

m-sb-4 How does @Transactional work?

ELI5
A receptionist (proxy) starts a DB envelope before your method and stamps commit or rollback after.
Interview answer
  • Rollback on RuntimeException by default — not checked unless rollbackFor.
  • this.foo() skips the proxy. HTTP inside a TX is a smell.
  • Project: we never called the payment gateway inside @Transactional; we CAS status then charged.

m-ms-1 Synchronous vs asynchronous communication

ELI5
Sync: phone call, wait for answer (REST/gRPC). Async: leave a voicemail (Kafka).
Interview answer

Sync for user-facing request/response. Async when you fan-out, decouple, or the work can finish later (email, indexing). Project: create order = sync DB; 'order created' event = Kafka to notify/search.

m-ms-2 How do you handle service failure?

ELI5
Don't wait forever. Don't retry forever. Don't take the whole system down with one sick friend.
Interview answer
  • Timeouts, retries with jitter, circuit breaker, bulkhead, fallback cache, 202+queue for non-critical.
  • K8s: readiness so traffic stops; liveness for deadlocks — don't mix them.

m-ms-3 Retry vs Circuit Breaker

ELI5
Retry: knock again. Circuit breaker: after enough failures, stop knocking so the door can recover.
Interview answer

Retries alone cause retry storms. CB + retry budget + jitter. Retry only idempotent calls (GET, or POST with idempotency key).

m-ms-4 What is the Saga pattern?

ELI5
A story of local transactions instead of one giant 2PC. If chapter 3 fails, play compensating chapters backwards.
Interview answer

Orchestration: a conductor. Choreography: events. Compensation can still fail → DLQ + reconcile. Project: book inventory → charge → if charge fails, release inventory.

m-ms-5 Consistency between services

ELI5
You cannot JOIN two service databases. You agree on events and eventually catch up.
Interview answer
  • Outbox in the same DB TX as the business write, then publish.
  • Idempotent consumers. Saga for multi-step. Unique keys for money.
  • Don't share a database 'just for a join'.

ELI5
INNER: only matching pairs. LEFT: keep every row from the left even if the right is empty (NULLs).

Students with no courses: LEFT JOIN enrollment. Paying customers only: INNER JOIN payments.

ELI5
A book index: jump to the page instead of reading every page.
Interview answer

B-tree on WHERE/JOIN/ORDER BY columns. Leftmost prefix of a composite index. They slow writes. Low-selectivity columns (boolean) rarely help.

m-sql-5 How do you troubleshoot a slow query?

ELI5
Ask the database for its plan, don't guess.
Interview answer
  • EXPLAIN ANALYZE, slow query log, look for seq scan on large tables, missing stats, N+1 from ORM.

m-jpa-1 LAZY vs EAGER loading

ELI5
LAZY: fetch the toys when the kid asks. EAGER: dump the whole toy box every time.
Interview answer

Collections default LAZY. EAGER on a hot API = accidental cartesian joins. After TX closes, lazy access → LazyInitializationException. Fix with fetch join / DTO query, not Open-Session-in-View as a crutch.

m-jpa-2 What is the N+1 problem?

ELI5
1 query for 100 orders + 100 queries for each customer = 101 trips.
Interview answer

Spot with show_sql / p6spy. Symptom: API time grows linearly with page size.

m-jpa-3 How do you resolve N+1?

ELI5
Ask for orders-and-customers in one (or a few) queries.
Interview answer
  • JOIN FETCH / @EntityGraph / DTO JPQL constructor.
  • @BatchSize as a bandage. Don't EAGER everything.

m-jpa-4 save() vs saveAndFlush()

ELI5
save: schedule SQL for later (until TX commit or flush). saveAndFlush: send SQL to the DB right now.
Interview answer
  • flush() still stays in the same transaction — rollback still undoes it.
  • Need generated ids, unique-constraint errors, or native queries to see your writes in-TX → flush.
  • saveAndFlush in a loop is a performance foot-gun (extra round trips).

m-kf-1 What is a Kafka partition?

A topic is a book. A partition is one ordered chapter/log. Order is guaranteed only inside a partition.
Interview answer

Key (customerId) hashes to a partition. More partitions = more consumer parallelism. Hot key = hot partition.

m-kf-2 What is a consumer group?

ELI5
A team sharing the work. Each partition is assigned to only one member of that group.
Interview answer

Same groupId = compete. Different groupId = each app gets a full copy (broadcast).

m-kf-3 Consumer crashes before committing an offset?

ELI5
The bookmark wasn't saved. On restart the group re-reads from the last committed offset → at-least-once → possible duplicates.
Interview answer

That's why consumers must be idempotent (unique event id). enable.auto.commit=false and commit after DB upsert is the usual Spring pattern.

m-kf-4 What is a Dead Letter Topic?

ELI5
The junk drawer for poison messages so one bad XML doesn't block the whole partition forever.
Interview answer

Retry with backoff, then publish to DLT + alert. Process DLT later. Don't swallow the error and commit — you'll lose the message.

m-kf-5 How do you make Kafka consumers idempotent?

ELI5
Treat each event as 'insert this id once'. The second delivery is a no-op.
Interview answer
  • UNIQUE(event_id) or upsert. Commit offset after the write succeeds.
  • Producer idempotence (enable.idempotence) stops producer retries from duplicating to Kafka — it does not stop consumer reprocessing.

cj-1 HashMap internals and how collisions are handled (Java 8+ treeification)

ELI5
Imagine a wall of lockers. You hash a key to pick a locker. If two keys pick the same locker, you hang them on a chain. If the chain gets long, you turn it into a balanced tree so search stays fast.
Interview answer

A HashMap stores key-value pairs in an array of buckets. Index is roughly (n - 1) & hash. Collisions originally used a linked list. From Java 8, if a bin has ≥ 8 nodes and the table is large enough (capacity ≥ 64), it treeifies into a red-black tree (O(log n) instead of O(n)). Resize doubles capacity when size > loadFactor × capacity (default 0.75). Tree bins untreeify on shrink.

Interview talking point: equal objects must have equal hashCodes. Mutating a key after insert breaks the map.

record User(String id, String name) {}

Map<String, User> users = new HashMap<>();
users.put("u1", new User("u1", "Asha"));
User found = users.get("u1"); // O(1) average

cj-2 HashMap vs ConcurrentHashMap vs Hashtable vs Collections.synchronizedMap

ELI5
HashMap is a fast notebook only one person should write in. Hashtable locks the whole notebook for every scribble. ConcurrentHashMap lets many people write in different pages at once.
Interview answer
  • HashMap: not thread-safe, 1 null key, fastest, can infinite-loop / corrupt on concurrent resize (legacy) or lose updates.
  • Hashtable: synchronized methods, no nulls, coarse lock, legacy — do not use in new code.
  • synchronizedMap: wraps a map with one lock on every operation; still not safe for compound actions (check-then-act) unless you lock on the map yourself.
  • ConcurrentHashMap: segment/bin-level concurrency, no nulls, weakly consistent iterators, atomic compute/merge. Use this for shared caches/counters.
ConcurrentHashMap<String, Integer> hits = new ConcurrentHashMap<>();
hits.merge(userId, 1, Integer::sum); // atomic increment

cj-3 equals() and hashCode() contract — break it and watch Set/Map lie

ELI5
The locker number (hashCode) must match the identity check (equals). If two things are 'equal' but have different locker numbers, the map will never find the second one.
Interview answer

Contract: if a.equals(b) then a.hashCode()==b.hashCode(). If you override one, override both. Use the same fields. Never use mutable fields as map keys.

Broken contract → HashSet 'duplicates', HashMap get returns null even though you put the object.

record Money(String currency, BigDecimal amount) {} // records generate both correctly

class BadId {
  int id;
  @Override public boolean equals(Object o) { return o instanceof BadId b && b.id == id; }
  // forgot hashCode → HashSet can store two "equal" BadIds
}

cj-4 Why is String immutable? Why is the class final? String pool and intern()

ELI5
A String is a sealed envelope. Nobody can rewrite the letters inside. That's why many people can share the same envelope (the string pool) safely.
Interview answer
  • Thread-safe sharing without locks.
  • String pool / intern: literals live in the pool; intern() reuses the pooled instance.
  • Security: class names, URLs, keys cannot be mutated under you.
  • hashCode is cached.
  • final class: subclasses cannot break pooling or equals.
  • == is reference; always use equals for content.
  • new String("abc") == "abc" is false (heap vs pool).
String s1 = new String("Java");
String s2 = s1.intern();
String s3 = "Java";
System.out.println(s2 == s3); // true
System.out.println(s1 == s2); // false

cj-5 + vs StringBuilder vs StringBuffer; substring leak; split on . and |

ELI5
Gluing strings in a loop is like photocopying a whole book every time you add one word. Use a notebook (StringBuilder) instead.
Interview answer
  • One expression with + is compiled to StringBuilder.
  • In loops, + is O(n²). Use StringBuilder / StringJoiner / Collectors.joining().
  • StringBuffer = synchronized StringBuilder (rarely needed).
  • Pre-Java 7u6 substring shared the backing array (memory leak). Modern JDKs copy.
  • split(".") and split("|") are regex — escape or Pattern.quote.

cj-6 final vs finally vs finalize(); static; initialization order

ELI5
final = cannot change. finally = always run the cleanup. finalize = old GC goodbye letter that Java no longer recommends.
Interview answer
  • static: one copy per class; static blocks run when the class loads.
  • Order: parent static → child static → parent instance fields/blocks → parent ctor → child instance → child ctor.
  • finalize() is deprecated; use try-with-resources / Cleaner.

cj-7 Overloading vs overriding; can you override static / constructors?

ELI5
Overloading is the same name with different ingredients (compile time). Overriding is a child rewriting a parent's recipe (runtime).
Interview answer
  • Static methods are hidden, not overridden. A x = new B(); x.staticF() calls A's.
  • Constructors are not inherited, so they cannot be overridden (they can be overloaded).
  • Cannot override final/private methods.
  • Covariant returns are allowed on overrides.
  • @Override always — compiler catches typos.
class A { static void f() { System.out.println("A"); } }
class B extends A { static void f() { System.out.println("B"); } }
A x = new B();
x.f(); // prints A — static dispatch by reference type

cj-8 What happens if you pass null to String vs Object overloads? 5 to int vs Integer?

ELI5
Java picks the most specific match. String is more specific than Object, so null prefers String. For 5, the primitive int overload wins over Integer (no boxing needed).
Interview answer
  • f(null) with f(Object) and f(String) → f(String). If you also have f(Integer), it becomes ambiguous.
  • f(5) with f(int) and f(Integer) → f(int).
  • Integer cache is −128..127; Integer a=128,b=128; a==b is false.

cj-9 Checked vs unchecked; try-with-resources; throw vs throws

ELI5
Checked exceptions are the compiler tapping your shoulder: handle this. Unchecked are programming bugs. try-with-resources is auto-closing the fridge so milk doesn't spoil.
Interview answer
  • Checked (IOException): recoverable, declared. Unchecked (RuntimeException): bugs.
  • Use checked sparingly (truly recoverable). Prefer domain RuntimeExceptions at service boundaries.
  • try-with-resources closes AutoCloseables LIFO; suppressed exceptions via getSuppressed().
  • throw raises; throws declares.
  • If try and finally both throw, finally's exception wins (unless TWR).
  • returning from finally swallows the try return — never do that.
try (var in = Files.newBufferedReader(path);
     var out = Files.newBufferedWriter(dest)) {
    in.transferTo(out);
} // both closed even if transfer fails

cj-10 Serialization, transient, marker interfaces, serialVersionUID

ELI5
Serialization is packing a toy into a box of bytes so it can travel. transient means 'don't put this piece in the box' (passwords, images, caches).
Interview answer
  • Serializable is a marker interface (no methods).
  • serialVersionUID: sender and receiver class versions must match or InvalidClassException.
  • Prefer JSON/Protobuf in APIs. Java serialization is fragile and a security risk if you deserialize untrusted bytes.
  • DTO without Serializable: Java built-in serialization won't apply; JSON mappers (Jackson) do not need Serializable.
public class UserDto implements Serializable {
    private static final long serialVersionUID = 1L;
    private String name;
    private transient byte[] profileImage; // skip in Java serialization
}

cj-11 ArrayList vs LinkedList; Collection vs List vs Set vs Map; HashSet vs LinkedHashSet

ELI5
ArrayList is a numbered row of seats (jump to seat 50 instantly). LinkedList is a conga line (to seat 50 you tap 49 people).
Interview answer
  • ArrayList: O(1) get, bad middle insert, great cache locality — default list.
  • LinkedList: almost never faster in real JVM due to pointer chasing. Use for rare deque cases or Deque API.
  • Collection: bag of things. List: ordered, duplicates. Set: unique. Map: key→value (not a Collection).
  • HashSet: unique, no order. LinkedHashSet: unique + insertion order. TreeSet: sorted.
  • Need unique elements in a large dataset: HashSet (or ConcurrentHashMap.newKeySet() if concurrent).

cj-12 Fail-fast vs fail-safe; ConcurrentModificationException

ELI5
Fail-fast iterators panic if someone rearranges the room while they're counting. Fail-safe iterators look at a photocopy.
Interview answer

CME happens when a fail-fast collection (ArrayList, HashMap) is structurally modified while iterating (enhanced-for or iterator), including another thread. Use iterator.remove(), CopyOnWriteArrayList, or ConcurrentHashMap.

forEach on HashMap: you iterate entries; you cannot forEach the map as if it were a List of keys without entrySet/keySet/values.

cj-13 Comparable vs Comparator; TreeMap

ELI5
Comparable is the object's own ranking ('I am taller'). Comparator is an external referee ('sort by salary').
Interview answer

compareTo should be consistent with equals for SortedSet/Map. TreeMap is a red-black tree, O(log n), no null keys unless comparator allows.

cj-14 Anonymous classes vs lambdas; default and static methods on interfaces; abstract class vs interface after Java 8

ELI5
A lambda is a tiny unnamed function. An anonymous class can still have fields and multiple methods. After Java 8, interfaces can bring default methods — but they still don't hold instance state like abstract classes.
Interview answer
  • Abstract class: state, constructors, non-public methods, single inheritance.
  • Interface: multiple inheritance of type, default/static/private methods, no instance fields (only constants).
  • Default methods were added so libraries (List.sort) could evolve without breaking every implementor.
  • Static methods on interfaces are namespaced utilities (Comparator.comparing).
  • Lambdas capture effectively-final locals; they aren't subclasses and can't implement two SAM methods.

cj-15 Strong vs weak vs soft vs phantom references

ELI5
A strong reference is a hand holding a balloon — GC won't take it. A weak reference is a string tied loosely — GC can pop it when it wants.
Interview answer

WeakHashMap keys can disappear when no strong refs remain — useful for canonical mappings. Soft refs are for caches that should survive until memory is tight. Phantom refs are for cleanup after finalization. Prefer explicit cache eviction over relying on GC.

cj-quiz Classic Java traps interviewers love

ELI5
These are 15-second landmines. Memorize the punchline.
Interview answer
  • 10 + 20 + "30" + 40 + 50 → 30304050 (add until the first string, then concatenate).
  • Integer a=128, b=128; a==b → false (cache is −128..127).

cj-16 Why List&lt;int&gt; is illegal; covariant arrays vs invariant generics

ELI5
Generics need objects (boxes), not raw ints. Arrays are sneaky: a Number[] variable can point at Integer[] and then blow up when you store a Double.
Interview answer

List<Integer> is not a List<Number> (invariance). Arrays are covariant and fail at runtime with ArrayStoreException. Prefer lists for type safety.

j8-1 Optional — practical usage (of vs ofNullable vs empty)

ELI5
Optional is a box that may hold a gift or be empty — so you stop poking null and getting NPE surprises.
Interview answer
  • Optional.of(x) NPE if x is null. ofNullable allows empty. empty() is explicit empty.
  • Use as return types, not fields/parameters. Don't Optional.ofNullable(x).get() blindly.
  • orElse vs orElseGet: orElse always evaluates the default (costly). orElseGet is lazy.
  • orElseThrow for required values. map/flatMap for pipelines.
Optional<User> user = repo.findById(id);

cc-1 Locking in Java: synchronized vs ReentrantLock vs ReadWriteLock; wait/notify

ELI5
A lock is a bathroom key. synchronized is a simple lock on the door. ReentrantLock is a fancy key with a timeout and a 'try'. wait() is sitting inside until someone notify()s you — you must already hold the key.
Interview answer

  • ReadWriteLock: many readers OR one writer. Helps read-heavy caches; writers can starve if you aren't careful.

}

Locks & Distributed Concurrency

ReentrantLock, RWLock, DB vs JVM, Redis, duplicate orders

lk-1 What happens if a thread acquires a ReentrantLock and never calls unlock()?

ELI5
It's like taking the only bathroom key and walking away forever. Everyone else waits at the door.
Interview answer
  • Other threads calling lock() block indefinitely (or until that thread dies — and even then the lock is not auto-released).
  • ReentrantLock is not tied to a monitor that the JVM releases on thread death the way some people assume. The hold count stays > 0. The lock is leaked.
  • Throughput collapses: request threads pile up, Tomcat pool saturates, liveness probe may still look 'up' until timeouts cascade.
  • If that thread is also waiting on something that needs the same lock (or a DB connection), you can deadlock the JVM.

lk-2 Why should unlock() normally be placed inside a finally block?

ELI5
Because exceptions are messy kids. If you drop the key only on the happy path, a crash leaves the door locked.
Interview answer
  • Any RuntimeException / Error / return between lock() and unlock() skips unlock() unless finally runs.
  • Pattern: lock → try { work } finally { unlock() }. Never unlock if you didn't acquire (tryLock false).
  • synchronized does this for you (monitor exit on method/block leave). That's the main safety advantage of synchronized.
lock.lock();
try {
    doWork();
} finally {
    lock.unlock(); // always release, even if doWork throws
}

lk-3 Difference between lock(), tryLock(), and lockInterruptibly()

ELI5
lock() waits forever. tryLock() knocks and leaves if nobody answers. lockInterruptibly() waits but will wake up if someone taps your shoulder (interrupt).
Interview answer
  • lock(): uninterruptible wait (interrupt is remembered, but you stay blocked until you get the lock). Risk: cannot cancel a stuck waiter easily.
  • tryLock() / tryLock(timeout): non-blocking or timed. Use for avoiding deadlock and for SLAs ('fail this request in 50ms').
  • lockInterruptibly(): blocking wait that throws InterruptedException. Use in thread pools you want to shut down cleanly.
if (!lock.tryLock(50, TimeUnit.MILLISECONDS)) {
    throw new BusyException("order lock contended");
}
try { /* ... */ } finally { lock.unlock(); }

lk-4 Can ReentrantLock be configured for fairness? Performance trade-off?

ELI5
Fair lock is a polite queue: first come, first served. Unfair lock is a crowded door: whoever is lucky grabs it — usually faster.
Interview answer
  • new ReentrantLock(true) is FIFO-ish: reduces barging and starvation.
  • Cost: extra CAS/queue parking, worse throughput, more context switches — especially under high contention.
  • Default (unfair) lets the releasing thread's neighbor barge in while the parked waiter is waking — often 5–10× better throughput.
  • Interview line: 'Fairness is for latency tails and avoiding starvation, not for QPS. I almost never enable it in hot paths.'

lk-5 What is a Read-Write Lock starvation scenario?

ELI5
Many kids keep reading the same comic. The writer (who needs the room empty) never gets a turn.
Interview answer

ReentrantReadWriteLock allows concurrent readers OR one writer. If readers keep arriving, a writer can wait a long time. That's writer starvation. Reader starvation can happen with write-heavy unfair locks too, but interviews usually mean writers blocked by a never-ending reader stream.

lk-6 Why can a writer starve when there are continuous readers?

ELI5
Each new reader says 'I'm just looking' and the lock policy may let them in while a writer is already waiting.
Interview answer
  • Non-fair RW lock: new readers barge if a read lock is already held — writer never sees zero readers.
  • Even fair mode: if you acquire read lock, do IO, and re-acquire in a loop, the writer waits for the whole burst.
  • Mitigations: fair RW lock; prefer StampedLock (optimistic read); cache with copy-on-write; don't hold read lock across IO; bound reader sections to microseconds.
  • Java's ReentrantReadWriteLock fair policy prefers the longest-waiting thread — writers get a better chance, still not a hard SLA.

lk-7 Optimistic locking vs pessimistic locking

ELI5
Pessimistic: lock the cookie jar before you look. Optimistic: take a photo of the jar, change it, and fail if someone else moved it.
Interview answer
  • Pessimistic: acquire lock first (synchronized / SELECT FOR UPDATE). Great when conflict is likely (inventory decrement).
  • Optimistic: read version, write with WHERE version=old, retry on 0 rows. Great when conflict is rare (user profile edits).
  • Java in-memory: optimistic ≈ AtomicInteger CAS / StampedLock tryOptimisticRead. Pessimistic ≈ synchronized / ReentrantLock.

lk-8 How is database optimistic locking different from Java synchronization?

ELI5
Java sync is a lock in this process's memory. DB optimistic locking is a version column the database checks — every pod sees it.
Interview answer
  • Java synchronized: same heap, same JVM, lost on restart, invisible to other instances.
  • JPA @Version: UPDATE ... SET version=version+1 WHERE id=? AND version=?. Second commit gets OptimisticLockException.
  • DB lock participates in transactions, isolation, and crash recovery. JVM lock does not.
@Entity
class Order {
  @Id Long id;
  @Version long version; // Hibernate includes it in UPDATE
}

lk-9 Can synchronized protect data stored in a database?

ELI5
No. synchronized is a lock on a Java object, not on a Postgres row. Another server has a different object.
Interview answer

It can serialize threads inside one instance before they hit the DB, which slightly reduces races on that node only. It cannot stop instance B. Use unique constraints, transactions, and row locks.

lk-10 What happens when two application instances update the same database record simultaneously?

ELI5

lk-12 What is a distributed lock, and when would you actually need one?

ELI5
A lock stored outside the JVM — Redis, ZooKeeper, DB row — so all instances agree who may do a job.

lk-13 Why can Redis-based distributed locking be tricky to implement correctly?

ELI5
Redis is fast sticky notes, not a judge in a courtroom. The note can expire, get lost in a partition, or be deleted by the wrong waiter.

lk-14 What happens if a JVM crashes while holding a distributed lock?

ELI5
The process is gone, but the 'I have the key' sticker might still be on Redis until TTL.
Interview answer
  • TTL/expiry: others wait, then take over. Too short TTL → split brain while the first JVM is actually still working (pause, GC, slow GC, network).
  • ZooKeeper/etcd session: ephemeral node disappears when heartbeat dies — faster failover, still need fencing so a 'zombie' JVM cannot commit.

lk-15 How can a timeout on a lock prevent one failure from blocking the entire application?

ELI5
If one waiter waits forever, every request behind it is a traffic jam. A timeout says 'this lane is closed, return 503'.
Interview answer
  • tryLock(timeout) / @Transactional timeout / HTTP client timeout / Redis lock TTL.
  • Fail fast + retry with jitter or let the user retry. Don't hold Tomcat threads on an unbounded lock.
  • Circuit breaker on a dependency is the same idea one level up.

lk-16 What is lock escalation, and can excessive locking create a scalability bottleneck?

ELI5
Lock escalation is when many small locks become one big lock (DB: row → page → table). Too many locks = everyone stands in one line.
Interview answer
  • Databases may escalate row locks to table locks under pressure — then writers serialize.
  • In Java: one global synchronized(this) on a singleton service is a table lock for your whole API.
  • Fine-grained keys (stripe locks per orderId) scale better than one ReentrantLock for all orders.
  • Lock convoying: threads wake, miss the lock, sleep — CPU looks idle, latency is awful.

lk-17 Why can holding a lock while performing a network call be dangerous?

ELI5
You locked the bathroom and then ordered pizza from inside. Everyone waits for the delivery guy.
Interview answer
  • Network is 10–100ms (or 30s on timeout). Lock hold time should be microseconds–milliseconds of CPU/memory work.
  • Effects: thread-pool exhaustion, deadlock (A holds lock, waits on B; B needs lock), GC pressure from piled threads, cascading timeouts.
  • Pattern: compute under lock / copy what you need / unlock / then HTTP. For DB: don't call payment gateway inside @Transactional.

lk-18 What happens when a synchronized method calls another synchronized method on the same object?

ELI5
Reentrant: you already have the key, so you walk back into the same room. You don't wait for yourself.
Interview answer
  • Java intrinsic locks and ReentrantLock are reentrant. Hold count increments; you must exit the same number of times.
  • This is why synchronized foo() can call synchronized bar() on this without deadlock.
  • It is NOT safe across two different objects — that's nested locking and deadlock territory (next question).
synchronized void a() { b(); }   // OK: same monitor
synchronized void b() { /* ... */ }

lk-19 How can nested locks across different services/classes create an unexpected deadlock?

ELI5
Service A takes lock Order then lock Wallet. Service B takes Wallet then Order. Two polite people each holding one door.
Interview answer
  • Classic: synchronized(order) { synchronized(wallet) } vs the reverse order on another thread.
  • Spring: @Transactional on OrderService plus synchronized on WalletService plus a Feign call that comes back into OrderService — lock order is no longer obvious.
  • Detect: jstack deadlock section. Prevent: global lock order, tryLock + backoff, don't nest, one lock per aggregate, DB as the only lock.

lk-20 Production: no Java race, but duplicate orders under high traffic — how do you investigate?

ELI5
The bug is often between pods, not inside one HashMap. Treat it as a distributed race until proven otherwise.
Interview answer
  • App sync: Is there a check-then-act (findByClientRequestId then save) without a unique index? Thread dumps won't show it across instances.
  • DB constraints: UNIQUE(idempotency_key) / UNIQUE(user_id, cart_hash). Missing unique = duplicates are allowed by the schema.
  • Transactions: two TXs both read 'no row' at READ COMMITTED, both insert. Isolation won't save you without uniqueness or SELECT FOR UPDATE on a parent row.
  • Idempotency: client retries + LB retries + gateway timeout retry. Same POST twice must return the first order id.
  • Distributed: 3 instances, each synchronized locally. Confirm replica count, correlation ids, insert timestamps milliseconds apart from different pod names.
  • Fix order: unique constraint first (safety net) → idempotency table → CAS status → only then Redis lock if you must serialize a side effect.

sc-6 @Transactional internals: propagation, isolation, rollback pitfalls; checked exceptions

ELI5
ELI5: @Transactional is a receptionist who starts a DB 'all or nothing' envelope before your method and stamps commit or rollback after.
Interview answer
  • Default: REQUIRED, isolation DEFAULT (usually READ_COMMITTED), rollback on RuntimeException/Error only — checked exceptions do not roll back unless rollbackFor=Exception.class.
  • Propagation: REQUIRED (join or start), REQUIRES_NEW (suspend and new), NESTED (savepoint), SUPPORTS, NOT_SUPPORTED, MANDATORY, NEVER.
  • Isolation: READ_UNCOMMITTED, READ_COMMITTED, REPEATABLE_READ, SERIALIZABLE. Phantom/non-repeatable reads depend on DB.
  • Pitfalls: self-invocation; catching exception inside method so proxy never sees it; calling external HTTP inside a long transaction; @Async inside transaction (see below).
@Transactional(rollbackFor = Exception.class)

sc-7 Exception in @Async method b() called from @Transactional a()

ELI5
a() starts a transaction on thread T1. b() runs later on thread T2 — it does not see T1's transaction (ThreadLocal). Exceptions in b() do not roll back a() unless you explicitly join on the Future and throw. The async exception may be lost on the Future.
Interview answer

Never do DB writes you need in the same TX inside @Async. Outbox pattern: commit event row in a(), publish after commit.

Repositories, transactions, queries

db-1 N+1 query problem — find and kill it

ELI5
You ask for 100 orders (1 query), then for each order you ask for the customer (100 queries). That's N+1.
Interview answer
  • Spot: show_sql / p6spy / datasource-proxy, slow logs, 101 queries for one API.
  • Fix: join fetch, @EntityGraph, batch size (@BatchSize), DTO JPQL constructor, Map instead of lazy loops.

db-2 Lazy vs eager; second-level cache; entity states

ELI5
Lazy: load the toy when the kid asks. Eager: dump the whole toy box every time — often too much.
Interview answer
  • Default many-to-one often eager; collections lazy. Prefer lazy + explicit fetch.
  • L2 cache (Ehcache/Redis via Hibernate): shares entities across sessions. Good for read-mostly ref data. Invalidation is the hard part. First-level cache is the Session itself.
  • States: transient (new), managed (persistent context), detached (TX closed), removed. persist/merge/remove/find/flush vs Spring Data save (persist or merge).

db-3 Indexes — when they help and hurt; composite keys; stored procedures and triggers

ELI5
An index is a book index: fast lookup, extra pages to update on every write.
Interview answer
  • Helps WHERE/JOIN/ORDER BY matching leftmost prefix of a composite index.
  • Hurts: too many indexes, low-selectivity columns (boolean), write-heavy tables, functions on columns that skip the index.
  • Composite key: two+ columns uniquely identify a row (@IdClass / @EmbeddedId).
  • Stored proc: compiled SQL on the server. Trigger: automatic SQL on insert/update/delete — hidden side effects, use sparingly.

db-4 SQL: salary &gt; manager; second highest; duplicates; student enrollments

ELI5
Self-join the employee table so each person sits next to their manager.
Interview answer -- salary greater than manager SELECT e.name, e.salary, m.name AS manager FROM employee e JOIN employee m ON e.manager_id = m.id WHERE e.salary > m.salary; -- second highest salary without LIMIT SELECT MAX(salary) FROM employee WHERE salary < (SELECT MAX(salary) FROM employee); -- duplicate rows SELECT email, COUNT(*) FROM users GROUP BY email HAVING COUNT(*) > 1; -- students and enrollments (LEFT JOIN keeps students with zero courses) SELECT s.name, c.course_name, e.grade FROM student s LEFT JOIN enrollment e ON e.student_id = s.student_id LEFT JOIN course c ON c.course_id = e.course_id; -- all courses and enrolled students SELECT c.course_name, s.name FROM course c LEFT JOIN enrollment e ON e.course_id = c.course_id LEFT JOIN student s ON s.student_id = e.student_id; SELECT s.name, AVG(e.grade) AS avg_grade FROM student s JOIN enrollment e ON e.student_id = s.student_id GROUP BY s.student_id, s.name; SELECT s.name FROM student s JOIN enrollment e ON e.student_id = s.student_id GROUP BY s.student_id, s.name HAVING AVG(e.grade) > 85; SELECT c.course_name, COUNT(e.student_id) AS students FROM course c LEFT JOIN enrollment e ON e.course_id = c.course_id GROUP BY c.course_id, c.course_name;

ELI5
  • Plan changed: missing/outdated stats, seq scan, lock wait, saturation, noisy neighbor, ORMs N+1, parameter sniffing.

ELI5

Kafka

Topics, consumers, exactly-once-ish patterns

kf-1 Topics, partitions, consumer groups, offsets, ACKs, replication

ELI5
A topic is a named log. Partitions are ordered lanes. A consumer group is a team sharing the work — each partition goes to one member. Offset is the bookmark. Replication is photocopies on other brokers.
Interview answer
  • acks=0 fire-forget; acks=1 leader; acks=all ISR — safest.
  • Replication: leader + followers. min.insync.replicas for durability.
  • auto.offset.reset: earliest vs latest only when no committed offset.

kf-2 A posts Kafka to B; B consumes and calls C's REST

ELI5
A is the mail sender, Kafka is the post office, B is the clerk who reads mail and phones C.
Interview answer @Service @RequiredArgsConstructor public class BListener { private final RestClient restClient; @KafkaListener(topics = "b-in", groupId = "service-b") public void onMessage(String xml) { CRequest body = xmlMapper.read(xml); // validate, map restClient.post().uri("http://service-c/api").body(body).retrieve().toBodilessEntity(); // commit offset after success (Spring default ack mode) } } 
Put timeouts + retries + DLQ on the HTTP call. Don't hold a DB transaction open while calling C.

kf-3 DB saved but Kafka publish failed — rollback / outbox

ELI5
Two systems (DB and Kafka) cannot share one ACID transaction easily. If you write DB then Kafka dies, you have ghost data.
Interview answer
  • Transactional Outbox: same DB TX writes business row + outbox row. A poller/CDC (Debezium) publishes to Kafka. Retry until Kafka accepts. Idempotent consumers downstream.
  • Don't: @Transactional around kafkaTemplate.send + repo.save and hope (send is async; XA 2PC is painful).
  • If Kafka succeeded and DB failed: idempotent producer keys + consumer dedupe.

kf-4 Consumer group: 3 apps on one topic; lag; down 30 min; duplicates; DLQ; ordering

ELI5
  • Same groupId: compete (share partitions). Different groupIds: each app gets every message (broadcast).
  • Lag: processing slower than produce. Check key hotspot, stop-the-world GC, downstream slowness, max.poll.interval exceeded (rebalance loops), too few partitions/consumers.
  • Consumer down 30 min: messages stay on broker until retention. On restart, resume from committed offset. If retention elapsed, data is gone.
  • Duplicates: at-least-once default. Idempotent consumer (unique key in DB).
  • Poison message: retry with backoff then DLQ topic + alert. Don't block the partition forever.
  • Ordering: one partition per key (customerId). One consumer per partition. Compaction for latest-per-key.

kf-5 Hot partition; broker down; Kafka vs RabbitMQ; producer/consumer tunables

ELI5
  • Hot partition: bad key (null or one customer). Use better key or sub-key hashing.
  • Broker down: ISR elects new leader if RF≥2. Producers with acks=all may fail if ISR < min.insync.
  • Kafka: durable log, replay, high throughput, partitioning. Rabbit: smarter routing, broker protocols, competing consumers without replay-as-a-log.
  • Producer: linger.ms, batch.size, compression, retries, idempotence, max.in.flight.
  • Consumer: max.poll.records, max.poll.interval, session.timeout, heartbeat.interval, fetch.min.bytes.

kf-health Consumer looks healthy but is not consuming; partition/broker down

ELI5
Healthy process ≠ making progress. The heartbeat can succeed while processing is stuck or assigned zero partitions.
Interview answer
  • Check: assigned partitions (actuator/kafka or logs), consumer group describe, lag per partition, max.poll.interval (long processing → kicked from group), paused listener, wrong topic/group, poison message retry loop, deserializer errors skipped.
  • One partition's broker/leader down: clients metadata refresh, new leader if RF>1. If RF=1, that partition is offline until broker returns.

kf-6 Idempotent Kafka consumer design; prevent loss when consumer dies; XML transform pipeline

ELI5

On consume: parse XML → validate → upsert by eventId (unique) → publish downstream. Commit offset only after unique insert succeeds. If publish is required, use outbox.

enable.idempotence on producer avoids dupes on retry to Kafka itself — not dupes from two consumer deliveries.

Production Scenarios

The 'what would you do' questions

pr-1 Duplicate payment — two identical requests at once

ELI5
Put a unique ticket number (idempotency key) on the payment. The second request finds the same ticket and returns the first result instead of charging again.
Interview answer
  • Client sends Idempotency-Key. Unique constraint on (key). First TX inserts and charges; second hits conflict and reads original status.
  • Don't call the payment provider inside a long DB lock — use state machine: NEW → PROCESSING → SUCCESS with compare-and-set.

pr-2 Double hotel booking — two users, one room

ELI5
The room row is a single cookie. Only one hand can grab it: UPDATE rooms SET status='BOOKED' WHERE id=? AND status='FREE' and check rows=1. Unique constraint on (room_id, night).
Interview answer

Optional short TTL lock in Redis for UX, but the DB constraint is the source of truth.

pr-3 REST API 30s because it calls three downstreams

ELI5
Don't stand in three queues one after another. Stand in all three at once (CompletableFuture / virtual threads), cache, cut payloads, set 200ms timeouts, bulk endpoints, or make the UX async (202 + poll).

pr-4 Kafka consumer down 30 minutes

ELI5
Mail piles up in the post office (until retention). When the consumer returns it continues from the last committed offset. Lag spike, then catch-up. If processing is slow, scale consumers (partitions ≥ consumers).

pr-5 Spring Boot CPU 95% and threads exploding; one K8s pod hot

ELI5
  • Thread dump: blocked on HTTP, JDBC, synchronized, or a runaway loop. Check pool sizes vs unbounded create.
  • One hot pod: sticky session, unlucky shard, missing readiness so one pod got all traffic, noisy neighbor limits, infinite retry storm to that replica, or a poison message unique to that instance's partition assignment.

pr-6 Memory climbs to OOMKilled; JWT 401; DB slow after millions of rows

ELI5
  • OOM: heap dump, caches, ByteBuf leak, hibernate session, logging huge XML.
  • JWT: see Security section.
  • DB: indexes, EXPLAIN, pagination, archive, N+1.

pr-7 Service C down — stop cascade; one slow service infects the system

ELI5
Timeouts + circuit breaker + bulkhead + fallback cache. Don't use infinite retries. Isolate thread pools per dependency. Queue non-critical work.

pr-8 Customer charged twice / payment workflow race

ELI5
Idempotency key + unique DB + provider refund/reconcile job. Identify with request ids in logs. Solve with CAS status transitions.

pr-9 Why retries alone make outages worse; graceful shutdown; config &amp; discovery

ELI5
Retries multiply traffic onto a dying service (retry storm). Combine retry (budgeted, jittered) with CB. Graceful shutdown: stop taking K8s endpoints (preStop + readiness off) then drain Tomcat. Config: Spring Cloud Config / K8s ConfigMap. Discovery: K8s DNS.

ad-3 SNS vs SQS vs Lambda; FIFO vs standard; why Lambda with SNS/SQS

ELI5
