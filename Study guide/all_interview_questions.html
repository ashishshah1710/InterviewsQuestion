591**Q11. `final`, `finally`, `finalize()` — differences?**
592**A.** `final`: non‑modifiable (var), non‑overridable (method), non‑extendable (class). `finally`: block that runs even when exceptions occur (except VM crash/`System.exit`). `finalize()`: deprecated/obsolete—unreliable GC hook.

603**Q15. `synchronized` method vs block?**
604**A.** Method locks on `this` or class object; block can lock an explicit monitor for a smaller critical section; prefer blocks to reduce contention.

606**Q16. `this` vs `super` usage?**

610**A.** Methods implemented in non‑Java (JNI), often for performance or system calls. Use sparingly.

612**Q18. `strictfp`?**

615**Q19. `assert` — when to use?**
616**A.** For internal invariants in non‑prod/test runs (enabled with `-ea`); never for user input validation in production.
617 
618**Q20. Order of initialization (static/instance)?**
619**A.** Static fields/blocks top‑down when class loads; then on each instantiation: instance fields → instance init blocks → constructor.

623## Section C — OOP, Overloading & Overriding
624 
625**Q21. Overloading vs overriding differences?**
626**A.** Overloading: same name, different parameter types/arity, resolved at compile time. Overriding: same signature in subclass, runtime dispatch; must respect return type covariance and throws rules.
627 
628**Q22. Can constructors be overridden?**
629**A.** No. They’re not inherited. They can be overloaded.
630 
631**Q23. Covariant return types?**
632**A.** Overriding method can return a subtype of the parent’s return type—helps fluency and builders.
633 
634**Q24. What can’t be overridden?**
635**A.** `final` methods, `static` methods (they are hidden), private methods (not visible), constructors.
636 
637**Q25. Method resolution with `List<Object>` vs `List<String>` overloads?**
638**A.** Due to type erasure, both become `List` at runtime; overloading on generic parameter types alone is ambiguous—compile‑time error.
639 
640**Q26. Which methods participate in dynamic dispatch?**
641**A.** Only instance (virtual) methods. Fields, `static` methods, and private methods do not; they’re resolved by reference type.
642 
643**Q27. Diamond problem in Java?**
644**A.** Multiple inheritance of state is disallowed; interfaces may provide default methods. If conflict, class must override to disambiguate.
645 
646**Q28. Liskov Substitution Principle (LSP) example?**
647**A.** Subtype must honor supertype contracts. E.g., overriding `List.add` to throw on valid inputs breaks LSP—avoid weakening preconditions.
648 
649**Q29. Prefer composition over inheritance—why?**
650**A.** Reduces tight coupling and fragile base class issues; enables delegation and easier testing; improves reusability.
651 
652**Q30. When to use `@Override`?**
653**A.** Always on overriding methods (and interface implementations) to let the compiler catch signature mismatches.

658 
659**Q31. Checked vs unchecked exceptions?**
660**A.** Checked: must be declared/handled (`IOException`). Unchecked: `RuntimeException` and subclasses (`NullPointerException`), not enforced. Use checked for recoverable conditions; unchecked for programming errors.
661 
662**Q32. Best practices for exception design?**
663**A.** Create meaningful custom exceptions, include context, avoid swallowing, don’t overuse checked, wrap/log at boundaries, and preserve cause (`new X(msg, cause)`).
664 
665**Q33. `try-with-resources`—how does it work?**
666**A.** Auto‑closes `AutoCloseable` resources in reverse order, even if exceptions occur. Suppressed exceptions are recorded via `Throwable.addSuppressed`.
667 
668**Q34. Exception rethrow vs wrap?**
669**A.** Rethrow to preserve type when caller can handle; wrap (with cause) to add context at boundaries (e.g., DAO → Service) while converting to domain exceptions.
670 
671**Q35. What happens if both `try` and `finally` throw?**
672**A.** Exception from `finally` suppresses the one from `try` (unless using try‑with‑resources where `try` exception is the primary and closes are suppressed).
673 
674**Q36. How to create an immutable, informative exception?**
675**A.** Extend `RuntimeException`/`Exception`, make fields `final`, include problem identifiers/IDs, override `getMessage()` to include key context (without PII).
676 
677**Q37. Difference between `throw` and `throws`?**
678**A.** `throw` actually raises an exception instance; `throws` declares that a method may propagate it.
679 
680**Q38. When to catch `Exception` broadly?**
681**A.** Rarely: top‑level boundaries (controllers/thread pools) to log and convert to standard responses. Avoid catching broadly in business logic.
682 
683**Q39. StackOverflowError vs OutOfMemoryError—can you catch them?**
684**A.** They’re `Error`s—indicative of serious problems; you *can* catch but shouldn’t rely on handling. Better to prevent via recursion limits and memory sizing.
685 
686**Q40. How to ensure resource cleanup if not using try‑with‑resources?**
687**A.** Use `try { ... } finally { closeQuietly(...) }` and design idempotent `close()`.

691## Section E — Generics & Type System
692 
693**Q41. Type erasure—what and why?**
694**A.** Generics are enforced at compile time and erased at runtime (to maintain backward compatibility with pre‑Java‑5 bytecode). No reified types; can’t do `new T[]`, or `instanceof List<String>`.
695 
696**Q42. PECS—what is it?**
697**A.** *Producer Extends, Consumer Super*: use `? extends T` when reading (producer); `? super T` when writing (consumer). Example: `void addAll(Collection<? super T> dst, Collection<? extends T> src)`.
698 
699**Q43. Invariance of generics?**
700**A.** `List<Integer>` is **not** a subtype of `List<Number>`. Use wildcards to widen.
701 
702**Q44. Bounded type parameters syntax?**
703**A.** `<T extends Comparable<T> & Serializable>` (class/interface bounds; at most one class, multiple interfaces).
704 
705**Q45. Why `List<int>` is illegal?**
706**A.** Generics require reference types; use wrapper `Integer` or specialized structures (e.g., Trove/fastutil) for primitives.
707 
708**Q46. How to create a generic method?**
709**A.** `<T> T head(List<T> list) { return list.get(0); }` — type parameter before return type.
710 
711**Q47. Why can’t you overload by generic parameter only?**
712**A.** Type erasure makes signatures identical (bridge methods aside), causing conflicts.
713 
714**Q48. What are raw types and why avoid them?**
715**A.** Omitting generic arguments (e.g., `List list`) disables type checking, causing unchecked warnings and potential `ClassCastException`.
716 
717**Q49. Wildcard capture—what is it?**
718**A.** Technique to treat `?` as a concrete type variable via helper methods, enabling safe mutation or transformation.
719 
720**Q50. Covariant arrays vs invariant generics pitfall?**
721**A.** Arrays are covariant (`Number[]` can reference `Integer[]`) and fail at runtime; generics are invariant and fail at compile time—prefer generics for type safety.

731**A.** Equal objects must have equal hash codes; otherwise lookups miss, causing logical duplication and broken sets/maps.

734**A.** Preserves insertion/access order (configurable). Useful for LRU caches with `removeEldestEntry`.

736**Q54. `TreeMap` characteristics?**
737**A.** Sorted by natural order or comparator; O(log n) operations; keys must be mutually comparable and consistent with equals.

745**Q57. Difference between `ArrayList` and `LinkedList`?**
746**A.** ArrayList: contiguous array, O(1) random access, costly middle insert/remove; LinkedList: nodes with pointers, O(1) insertion/removal at ends, poor cache locality.

766## Section G — Concurrency, Threads & JMM
767 
768**Q61. Explain the Java Memory Model (JMM) briefly.**
769**A.** Specifies visibility and ordering guarantees between threads. `happens‑before` edges (locks, volatile writes→reads, thread start/join, completion of constructor before publication) ensure visibility; without HB, data races cause stale reads.
770 
771**Q62. Atomicity vs visibility vs ordering?**
772**A.** Atomicity: operation completes indivisibly. Visibility: writes by one thread seen by others. Ordering: reordering constraints. `volatile` gives visibility/ordering; locks give all three via mutual exclusion + HB.
773 
774**Q63. `volatile` pitfalls?**
775**A.** ++ is not atomic; compound actions require locks/atomics. Volatile only good for independent writes/reads and publishing immutable objects.
776 
777**Q64. Deadlock causes and prevention?**
778**A.** Circular wait, hold‑and‑wait, mutual exclusion, no preemption. Prevent by locking in fixed order, using timeouts (`tryLock`), finer granularity, or avoiding nested locks.
779 
780**Q65. Difference between `synchronized` and `ReentrantLock`?**
781**A.** `ReentrantLock` offers try/timed lock, interruptible waits, fair ordering, and `Condition`s; `synchronized` is simpler with implicit release.
782 
783**Q66. Explain thread states.**
784**A.** NEW, RUNNABLE, BLOCKED (monitor), WAITING (wait/join), TIMED\_WAITING (sleep/awaitNanos), TERMINATED.
785 
786**Q67. How does `ExecutorService` improve concurrency?**
787**A.** Manages thread pools, work queues, and scheduling; decouples task submission (`Runnable`/`Callable`) from execution; reduces creation overhead; enables back‑pressure via queue bounds.
788 
789**Q68. `Future` vs `CompletableFuture`?**
790**A.** `Future` represents a pending result (blocking get, no chaining). `CompletableFuture` enables async pipelines (`thenApply`, `thenCompose`), non‑blocking callbacks, and combinators (`allOf/anyOf`).
791 
792**Q69. Producer‑Consumer with `BlockingQueue`—why better than wait/notify?**
793**A.** Simpler, less error‑prone, supports bounded queues (back‑pressure) and interruption; hides low‑level coordination.
794 
795**Q70. ThreadLocal—use cases and risks?**
796**A.** Store per‑thread state (e.g., request IDs, formatters). Risk: memory leaks in thread pools if not cleared; use `remove()`.
797 
798**Q71. `ForkJoinPool` vs `ThreadPoolExecutor`?**
799**A.** FJP uses work‑stealing for fine‑grained tasks (divide‑and‑conquer). TPE is general‑purpose with configurable queues/rejection policies.
800 
801**Q72. Safe publication patterns?**
802**A.** (1) Final fields set in constructor; (2) volatile reference; (3) holding lock during publication; (4) using thread‑safe containers.
803 
804**Q73. Avoiding priority inversion/starvation?**
805**A.** Use fair locks when necessary, keep critical sections short, avoid unbounded queues; monitor with thread dumps.
806 
807**Q74. Rejection policies in thread pools?**
808**A.** `AbortPolicy` (default), `CallerRunsPolicy` (back‑pressure), `DiscardPolicy`, `DiscardOldestPolicy`. Choose based on SLA.
809 
810**Q75. How to detect deadlocks in prod?**
811**A.** Thread dumps (`jstack`), JMX tools, APMs; look for `Found one Java-level deadlock` sections.

830**A.** Static collections, caches without eviction, listeners not deregistered, ThreadLocals in pools, retaining large arrays or substrings (old JDKs). Use heap dumps and dominator trees to analyze.
