**Q41. Type erasure—what and why?**
**A.** Generics are enforced at compile time and erased at runtime (to maintain backward compatibility with pre‑Java‑5 bytecode). No reified types; can’t do `new T[]`, or `instanceof List<String>`.

**Q42. PECS—what is it?**
**A.** *Producer Extends, Consumer Super*: use `? extends T` when reading (producer); `? super T` when writing (consumer). Example: `void addAll(Collection<? super T> dst, Collection<? extends T> src)`.

**Q43. Invariance of generics?**
**A.** `List<Integer>` is **not** a subtype of `List<Number>`. Use wildcards to widen.

**Q44. Bounded type parameters syntax?**
**A.** `<T extends Comparable<T> & Serializable>` (class/interface bounds; at most one class, multiple interfaces).

**Q45. Why `List<int>` is illegal?**
**A.** Generics require reference types; use wrapper `Integer` or specialized structures (e.g., Trove/fastutil) for primitives.

**Q46. How to create a generic method?**
**A.** `<T> T head(List<T> list) { return list.get(0); }` — type parameter before return type.

**Q47. Why can’t you overload by generic parameter only?**
**A.** Type erasure makes signatures identical (bridge methods aside), causing conflicts.

**Q48. What are raw types and why avoid them?**
**A.** Omitting generic arguments (e.g., `List list`) disables type checking, causing unchecked warnings and potential `ClassCastException`.

**Q49. Wildcard capture—what is it?**
**A.** Technique to treat `?` as a concrete type variable via helper methods, enabling safe mutation or transformation.

**Q50. Covariant arrays vs invariant generics pitfall?**
**A.** Arrays are covariant (`Number[]` can reference `Integer[]`) and fail at runtime; generics are invariant and fail at compile time—prefer generics for type safety.

        this.paymentClient = paymentClient;

        Payment payment = paymentRepository.findById(paymentId)

        if ("SUCCESS".equals(payment.getStatus())) {

            return new PaymentResponse("ALREADY_PROCESSED");

        }
  
        payment.setStatus("PROCESSING");

        paymentRepository.save(payment);
 
        PaymentResponse response = paymentClient.charge(

                payment.getAmount()

        );
 
        if (response.isSuccess()) {

            payment.setStatus("SUCCESS");

        } else {

            payment.setStatus("FAILED");

        }
 
        paymentRepository.save(payment);
 
        return response;

    }

# Core Java 

## Section A — Strings & Immutability

**Q1. Why is `String` immutable in Java? What are the benefits?**
**A.** Immutability: value and hash are fixed after creation. Benefits: (1) Thread‑safety without synchronization; (2) String pool interning for memory sharing; (3) Security—strings used in classpaths, DB URLs, and keys cannot be altered; (4) Safe caching and hash code memorization.

**Q2. What is the String pool? How does interning work?**
**A.** The pool stores one canonical instance per literal. `"a" + "b"` at compile time goes to pool as `"ab"`. `new String("x")` creates a heap object, 

Interning means moving a string into the String Pool and reusing pooled references.

Method: public String intern()


If the string already exists in the pool → returns the pooled reference.
If it’s not in the pool → adds it and returns the new pooled reference.

Example:
String s1 = new String("Java");
String s2 = s1.intern();
String s3 = "Java";

System.out.println(s2 == s3); // true → both refer to pooled object
System.out.println(s1 == s2); // false → s1 still points to heap object

**Q3. `==` vs `.equals()` for Strings?**
**A.** `==` compares references; `.equals()` compares content. Pooling can make `==` true for literals but never rely on it—always use `.equals()` for content.

**Q4. Why is `String` `final`?**
**A.** To enforce immutability—subclasses can’t override methods (like `hashCode()`/`equals()`/`charAt`) to break invariants or pooling semantics.

**Q5. String concatenation performance: `+` vs `StringBuilder`?**
**A.** In a single expression, the compiler uses `StringBuilder` under the hood.
       In loops, repeated `+` creates many builders; Time Complexity: O(n²) for large loops.
       Heap impact: Thousands of intermediate string objects.

	   prefer explicit `StringBuilder` or `StringJoiner`. For streams, use `Collectors.joining()`. 

 StringBuffer: Almost same as StringBuilder but thread-safe.
               Uses synchronized methods, so slightly slower.
               Best used when multiple threads modify the same string.

**Q6. What does `substring()` do pre‑Java 7u6 vs now?**
**A.** Historically it shared the original char array (risking memory leaks); modern JDKs copy the necessary range, removing the leak but increasing copy cost.

**Q7. How to split a string safely on `.` and `|`?**
**A.** These are regex metacharacters; escape or use `Pattern.quote(delimiter)`.

**Q8. When to use `String.intern()` in high‑load services?**
**A.** Rarely. It can reduce memory for highly repetitive identifiers but risks perm/metaspace pressure (older JDKs) and lock contention. Prefer app‑level caches.

Performance Comparison
Aspect	Without Interning	With Interning
Memory	Multiple copies of the same string → high heap usage	Single reference reused → lower memory footprint
GC Impact	More objects → frequent GC	Less GC pressure
CPU Overhead	No lookup → faster	Lookup in SCP (hash-based) → slightly slower
Best Use Case	Unique strings	Heavy repetition

**Q9. Why does `new String("abc") == "abc"` return false?**
**A.** Different objects: heap vs pooled literal. `.equals()` would be true.

**Q10. Best way to build CSV safely?**
**A.** Use `StringJoiner`/`Collectors.joining()`; escape quotes/commas properly; prefer a CSV library for correctness.

## Section B — Core Keywords & Language Features

**Q11. `final`, `finally`, `finalize()` — differences?**
**A.** `final`: non‑modifiable (var), non‑overridable (method), non‑extendable (class). `finally`: block that runs even when exceptions occur (except VM crash/`System.exit`). `finalize()`: deprecated/obsolete—unreliable GC hook.

**Q12. `static` keyword uses?**
**A.** Class‑level members, single copy shared by instances; static initializer blocks; utility methods; inner `static` classes not linked to outer instance.

**Q13. `volatile` — what does it guarantee?**
**A.** Visibility + ordering (happens‑before on write/read), not atomicity for compound actions. Suitable for flags; not for increments.

**Q14. `transient` field — effect during serialization?**
**A.** Field is skipped. Often used for caches, passwords, or derived fields; reinitialize in `readObject`.

**Q15. `synchronized` method vs block?**
**A.** Method locks on `this` or class object; block can lock an explicit monitor for a smaller critical section; prefer blocks to reduce contention.

**Q16. `this` vs `super` usage?**
**A.** `this` for current instance; `super` to access parent members/constructors. Constructor must call `super(...)` as first statement (implicit `super()` if omitted).

**Q17. `native` methods?**
**A.** Methods implemented in non‑Java (JNI), often for performance or system calls. Use sparingly.

**Q18. `strictfp`?**
**A.** Enforces IEEE‑754 floating point semantics for cross‑platform consistency.

**Q19. `assert` — when to use?**
**A.** For internal invariants in non‑prod/test runs (enabled with `-ea`); never for user input validation in production.

**Q20. Order of initialization (static/instance)?**
**A.** Static fields/blocks top‑down when class loads; then on each instantiation: instance fields → instance init blocks → constructor.

---

## Section C — OOP, Overloading & Overriding

**Q21. Overloading vs overriding differences?**
**A.** Overloading: same name, different parameter types/arity, resolved at compile time. Overriding: same signature in subclass, runtime dispatch; must respect return type covariance and throws rules.

**Q22. Can constructors be overridden?**
**A.** No. They’re not inherited. They can be overloaded.

**Q23. Covariant return types?**
**A.** Overriding method can return a subtype of the parent’s return type—helps fluency and builders.

**Q24. What can’t be overridden?**
**A.** `final` methods, `static` methods (they are hidden), private methods (not visible), constructors.

**Q25. Method resolution with `List<Object>` vs `List<String>` overloads?**
**A.** Due to type erasure, both become `List` at runtime; overloading on generic parameter types alone is ambiguous—compile‑time error.

**Q26. Which methods participate in dynamic dispatch?**
**A.** Only instance (virtual) methods. Fields, `static` methods, and private methods do not; they’re resolved by reference type.

**Q27. Diamond problem in Java?**
**A.** Multiple inheritance of state is disallowed; interfaces may provide default methods. If conflict, class must override to disambiguate.

**Q28. Liskov Substitution Principle (LSP) example?**
**A.** Subtype must honor supertype contracts. E.g., overriding `List.add` to throw on valid inputs breaks LSP—avoid weakening preconditions.

**Q29. Prefer composition over inheritance—why?**
**A.** Reduces tight coupling and fragile base class issues; enables delegation and easier testing; improves reusability.

**Q30. When to use `@Override`?**
**A.** Always on overriding methods (and interface implementations) to let the compiler catch signature mismatches.

---

## Section D — Exceptions & Error Handling

**Q31. Checked vs unchecked exceptions?**
**A.** Checked: must be declared/handled (`IOException`). Unchecked: `RuntimeException` and subclasses (`NullPointerException`), not enforced. Use checked for recoverable conditions; unchecked for programming errors.

**Q32. Best practices for exception design?**
**A.** Create meaningful custom exceptions, include context, avoid swallowing, don’t overuse checked, wrap/log at boundaries, and preserve cause (`new X(msg, cause)`).

**Q33. `try-with-resources`—how does it work?**
**A.** Auto‑closes `AutoCloseable` resources in reverse order, even if exceptions occur. Suppressed exceptions are recorded via `Throwable.addSuppressed`.

**Q34. Exception rethrow vs wrap?**
**A.** Rethrow to preserve type when caller can handle; wrap (with cause) to add context at boundaries (e.g., DAO → Service) while converting to domain exceptions.

**Q35. What happens if both `try` and `finally` throw?**
**A.** Exception from `finally` suppresses the one from `try` (unless using try‑with‑resources where `try` exception is the primary and closes are suppressed).

**Q36. How to create an immutable, informative exception?**
**A.** Extend `RuntimeException`/`Exception`, make fields `final`, include problem identifiers/IDs, override `getMessage()` to include key context (without PII).

**Q37. Difference between `throw` and `throws`?**
**A.** `throw` actually raises an exception instance; `throws` declares that a method may propagate it.

**Q38. When to catch `Exception` broadly?**
**A.** Rarely: top‑level boundaries (controllers/thread pools) to log and convert to standard responses. Avoid catching broadly in business logic.

**Q39. StackOverflowError vs OutOfMemoryError—can you catch them?**
**A.** They’re `Error`s—indicative of serious problems; you *can* catch but shouldn’t rely on handling. Better to prevent via recursion limits and memory sizing.

**Q40. How to ensure resource cleanup if not using try‑with‑resources?**
**A.** Use `try { ... } finally { closeQuietly(...) }` and design idempotent `close()`.

---

## Section E — Generics & Type System

**Q41. Type erasure—what and why?**
**A.** Generics are enforced at compile time and erased at runtime (to maintain backward compatibility with pre‑Java‑5 bytecode). No reified types; can’t do `new T[]`, or `instanceof List<String>`.

**Q42. PECS—what is it?**
**A.** *Producer Extends, Consumer Super*: use `? extends T` when reading (producer); `? super T` when writing (consumer). Example: `void addAll(Collection<? super T> dst, Collection<? extends T> src)`.

**Q43. Invariance of generics?**
**A.** `List<Integer>` is **not** a subtype of `List<Number>`. Use wildcards to widen.

**Q44. Bounded type parameters syntax?**
**A.** `<T extends Comparable<T> & Serializable>` (class/interface bounds; at most one class, multiple interfaces).

**Q45. Why `List<int>` is illegal?**
**A.** Generics require reference types; use wrapper `Integer` or specialized structures (e.g., Trove/fastutil) for primitives.

**Q46. How to create a generic method?**
**A.** `<T> T head(List<T> list) { return list.get(0); }` — type parameter before return type.

**Q47. Why can’t you overload by generic parameter only?**
**A.** Type erasure makes signatures identical (bridge methods aside), causing conflicts.

**Q48. What are raw types and why avoid them?**
**A.** Omitting generic arguments (e.g., `List list`) disables type checking, causing unchecked warnings and potential `ClassCastException`.

**Q49. Wildcard capture—what is it?**
**A.** Technique to treat `?` as a concrete type variable via helper methods, enabling safe mutation or transformation.

**Q50. Covariant arrays vs invariant generics pitfall?**
**A.** Arrays are covariant (`Number[]` can reference `Integer[]`) and fail at runtime; generics are invariant and fail at compile time—prefer generics for type safety.

## Section F — Collections & Maps

**Q51. HashMap internals—buckets, collisions, resize?**
**A.** Hash → index; bucket holds nodes. On collision, chain via linked list; from Java 8, large chains treeify (balanced red‑black tree) past threshold (default 8) when table big enough; resize doubles capacity when load factor exceeded (default 0.75).

**Q52. Why `hashCode()` and `equals()` contract matters?**
**A.** Equal objects must have equal hash codes; otherwise lookups miss, causing logical duplication and broken sets/maps.

**Q53. `LinkedHashMap` vs `HashMap`?**
**A.** Preserves insertion/access order (configurable). Useful for LRU caches with `removeEldestEntry`.

**Q54. `TreeMap` characteristics?**
**A.** Sorted by natural order or comparator; O(log n) operations; keys must be mutually comparable and consistent with equals.

**Q55. `ConcurrentHashMap` design?**
**A.** Fine‑grained concurrency; no global lock; operations are thread‑safe and non‑blocking for reads; supports atomic compound operations via `compute`, `merge`.

**Q56. Fail‑fast vs fail‑safe iterators?**
**A.** Fail‑fast (ArrayList/HashMap) throw `ConcurrentModificationException` on structural change; fail‑safe (CopyOnWriteArrayList, ConcurrentHashMap) iterate over a snapshot/weakly consistent view.

**Q57. Difference between `ArrayList` and `LinkedList`?**
**A.** ArrayList: contiguous array, O(1) random access, costly middle insert/remove; LinkedList: nodes with pointers, O(1) insertion/removal at ends, poor cache locality.

**Q58. When to use `CopyOnWriteArrayList`?**
**A.** Read‑heavy, infrequent writes; iteration without locks; expensive writes due to full copy.

**Q59. PriorityQueue vs Deque use cases?**
**A.** PQ maintains heap order for min/max retrieval; Deque for double‑ended queues, stacks, sliding window problems.

**Q60. How to implement LRU cache quickly?**
**A.** Use `LinkedHashMap` with access‑order `true` and override `removeEldestEntry`.

```java
Map<K,V> lru = new LinkedHashMap<K,V>(16, 0.75f, true) {
  protected boolean removeEldestEntry(Map.Entry<K,V> e) { return size() > 1000; }
  
};
```

## Section G — Concurrency, Threads & JMM

**Q61. Explain the Java Memory Model (JMM) briefly.**
**A.** Specifies visibility and ordering guarantees between threads. `happens‑before` edges (locks, volatile writes→reads, thread start/join, completion of constructor before publication) ensure visibility; without HB, data races cause stale reads.

**Q62. Atomicity vs visibility vs ordering?**
**A.** Atomicity: operation completes indivisibly. Visibility: writes by one thread seen by others. Ordering: reordering constraints. `volatile` gives visibility/ordering; locks give all three via mutual exclusion + HB.

**Q63. `volatile` pitfalls?**
**A.** ++ is not atomic; compound actions require locks/atomics. Volatile only good for independent writes/reads and publishing immutable objects.

**Q64. Deadlock causes and prevention?**
**A.** Circular wait, hold‑and‑wait, mutual exclusion, no preemption. Prevent by locking in fixed order, using timeouts (`tryLock`), finer granularity, or avoiding nested locks.

**Q65. Difference between `synchronized` and `ReentrantLock`?**
**A.** `ReentrantLock` offers try/timed lock, interruptible waits, fair ordering, and `Condition`s; `synchronized` is simpler with implicit release.

**Q66. Explain thread states.**
**A.** NEW, RUNNABLE, BLOCKED (monitor), WAITING (wait/join), TIMED\_WAITING (sleep/awaitNanos), TERMINATED.

**Q67. How does `ExecutorService` improve concurrency?**
**A.** Manages thread pools, work queues, and scheduling; decouples task submission (`Runnable`/`Callable`) from execution; reduces creation overhead; enables back‑pressure via queue bounds.

**Q68. `Future` vs `CompletableFuture`?**
**A.** `Future` represents a pending result (blocking get, no chaining). `CompletableFuture` enables async pipelines (`thenApply`, `thenCompose`), non‑blocking callbacks, and combinators (`allOf/anyOf`).

**Q69. Producer‑Consumer with `BlockingQueue`—why better than wait/notify?**
**A.** Simpler, less error‑prone, supports bounded queues (back‑pressure) and interruption; hides low‑level coordination.

**Q70. ThreadLocal—use cases and risks?**
**A.** Store per‑thread state (e.g., request IDs, formatters). Risk: memory leaks in thread pools if not cleared; use `remove()`.

**Q71. `ForkJoinPool` vs `ThreadPoolExecutor`?**
**A.** FJP uses work‑stealing for fine‑grained tasks (divide‑and‑conquer). TPE is general‑purpose with configurable queues/rejection policies.

**Q72. Safe publication patterns?**
**A.** (1) Final fields set in constructor; (2) volatile reference; (3) holding lock during publication; (4) using thread‑safe containers.

**Q73. Avoiding priority inversion/starvation?**
**A.** Use fair locks when necessary, keep critical sections short, avoid unbounded queues; monitor with thread dumps.

**Q74. Rejection policies in thread pools?**
**A.** `AbortPolicy` (default), `CallerRunsPolicy` (back‑pressure), `DiscardPolicy`, `DiscardOldestPolicy`. Choose based on SLA.

**Q75. How to detect deadlocks in prod?**
**A.** Thread dumps (`jstack`), JMX tools, APMs; look for `Found one Java-level deadlock` sections.

## Section H — Memory, GC & Performance

**Q76. Heap vs stack vs metaspace?**
**A.** Stack: per‑thread frames/locals. Heap: objects. Metaspace: class metadata (native memory). GC manages heap; metaspace grows until limits.

**Q77. GC algorithms overview?**
**A.** Generational GC: young (Eden→S0/S1) minor GCs, tenuring to old; major/full GC compacts. Modern JDKs include G1/Parallel/Serial/ZGC/Shenandoah (choose per latency/throughput needs).

**Q78. Escape analysis and scalar replacement?**
**A.** JIT can allocate on stack or eliminate objects if they don’t escape method/thread, improving performance.

**Q79. Why avoid premature optimization?**
**A.** Optimize hotspots backed by profiling (JFR, async‑profiler). Micro‑bench with JMH; beware of dead‑code elimination and warm‑up effects.

**Q80. Memory leak sources in Java?**
**A.** Static collections, caches without eviction, listeners not deregistered, ThreadLocals in pools, retaining large arrays or substrings (old JDKs). Use heap dumps and dominator trees to analyze.

## Section I — I/O, Serialization, NIO.2

**Q81. `Serializable` pitfalls?**
**A.** Insecure/unversioned payloads, fragile to class changes, performance overhead. Prefer JSON/Proto with explicit schemas. If using Java serialization, define `serialVersionUID` and validate inputs.

**Q82. `Externalizable` vs `Serializable`?**
**A.** `Externalizable` gives full control over (de)serialization via `writeExternal/readExternal`; requires no‑arg constructor.

**Q83. try‑with‑resources and `AutoCloseable` ordering?**
**A.** Resources are closed LIFO; suppressed exceptions accessible via `Throwable.getSuppressed()`.

**Q84. NIO vs IO?**
**A.** NIO offers channels, buffers, selectors; non‑blocking IO and memory‑mapped files for high throughput servers.

**Q85. File watching and async IO in Java 8?**
**A.** `WatchService` for directory changes; `AsynchronousFileChannel` for async file operations.

## Section J — Annotations, Reflection, ClassLoaders

**Q86. How do annotations work at runtime?**
**A.** Retention policy `RUNTIME` makes them available via reflection; frameworks scan classes/methods/parameters to build metadata (e.g., Spring).

**Q87. Meta‑annotations you should know?**
**A.** `@Retention`, `@Target`, `@Inherited`, `@Documented`, `@Repeatable`.

**Q88. Reflection costs and safety?**
**A.** Slower, breaks encapsulation, security risks; cache reflective lookups; prefer method handles where possible.

**Q89. ClassLoader hierarchy?**
**A.** Bootstrap → Extension/Platform → Application → custom loaders; parent‑first delegation, but frameworks can use child‑first.

**Q90. Common `NoClassDefFoundError` vs `ClassNotFoundException`?**
**A.** `ClassNotFoundException` is checked (loader can’t find class when asked). `NoClassDefFoundError` occurs when a previously found class fails to load/initialize at runtime.

## Section K — Design Patterns & Idioms (Core Java use)

**Q91. Builder vs telescoping constructors?**
**A.** Builder avoids constructor explosion, improves readability/immutability; especially useful for many optional params.

**Q92. Strategy pattern with lambdas?**
**A.** Replace small Strategy classes with `Function`/`Predicate`/`Comparator` implementations using lambdas.

**Q93. Singleton pitfalls and fixes?**
**A.** Lazy init race conditions. Prefer enum singletons or initialize‑on‑demand holder idiom; avoid double‑checked locking before `volatile` fix.

**Q94. Template method vs callback?**
**A.** Template: inheritance‑based hooks. Callback: composition with functional interfaces—more flexible in Java 8+.

**Q95. Decorator vs inheritance for behavior extension?**
**A.** Decorator adds behavior at runtime without subclass explosion; works well with `InputStream`/`Reader` chains.

## Section L — Java 8: Streams, Lambdas, Date/Time

**Q96. Intermediate vs terminal ops?**
**A.** Intermediate are lazy and return streams (`map`, `filter`); terminal triggers evaluation (`collect`, `reduce`, `forEach`).

**Q97. `map` vs `flatMap`?**
**A.** `map` transforms 1→1; `flatMap` flattens nested streams (e.g., Stream\<List<T>> → Stream<T>). Useful for one‑to‑many mappings.

**Q98. Common stream pitfalls in prod?**
**A.** Side‑effects in lambdas, poor readability, NPE on `null` streams, using parallel streams on IO‑bound tasks, boxing/unboxing overhead.

**Q99. Custom collectors—when needed?**
**A.** For non‑standard reductions (e.g., top‑K with heap) or when needing concurrent accumulation. Implement `Supplier`, `Accumulator`, `Combiner`, `Finisher`.

**Q100. New Date/Time API advantages?**
**A.** Immutable, thread‑safe, clear types (`Instant`, `LocalDateTime`, `ZonedDateTime`), better zone handling with `ZoneId`, fluent adjusters.

**Q101. How to compute start/end of day safely?**
**A.** Use `LocalDate.now(zone).atStartOfDay(zone)` and `LocalDate.now(zone).plusDays(1).atStartOfDay(zone).minusNanos(1)` to respect DST.

**Q102. Converting between `Date` and `Instant`?**
**A.** `Date.from(instant)` and `date.toInstant()`.

## Section M — Tricky/Corner Cases & Quiz‑style

**Q103. What prints?**

```java
System.out.println(10 + 20 + "30" + 40 + 50);
```

**A.** `"30304050"`? No → `30 + "30"` → `"3030" + 40 + 50` → `"303040" + 50` → `"30304050"`. (Left‑to‑right; numbers before first string are added.)

**Q104. Autoboxing trap:**

```java
Integer a = 128, b = 128; System.out.println(a == b);
```

**A.** `false`. Integer cache ranges −128..127.

**Q105. Overloaded `null` call:**

```java
void f(Object o) {} void f(String s) {}
f(null);
```

**A.** Chooses most specific → `f(String)`.

**Q106. Static vs instance hidden:**

```java
class A { static void f(){System.out.println("A");} }
class B extends A { static void f(){System.out.println("B");} }
A x = new B(); x.f();
```

**A.** Prints `A` (static method hidden, resolved by reference type).

**Q107. `equals` without `hashCode` in HashSet?**
**A.** Violates contract → duplicates may appear and lookups fail.

**Q108. `finally` overrides `return`?**

```java
int g(){ try { return 1; } finally { return 2; } }
```

**A.** Returns `2` (discouraged!).

**Q109. Double‑checked locking and `volatile`?**
**A.** The instance field must be `volatile` to prevent reorderings causing half‑constructed objects to be visible.

**Q110. Stream short‑circuit behavior?**
**A.** Ops like `findFirst`, `anyMatch`, `limit` can stop traversal early; useful for performance.

**Q111. `remove` during enhanced for?**
**A.** Use iterator’s `remove()`; direct `list.remove()` causes `ConcurrentModificationException`.

**Q112. `Optional.of(null)`?**
**A.** NPE. Use `Optional.ofNullable(x)`.

**Q113. `StringBuilder` thread‑safety?**
**A.** Not thread‑safe; `StringBuffer` is synchronized (rarely worth it). Prefer confinement or higher‑level sync.

**Q114. `HashSet` contains `null`?**
**A.** Yes (single null allowed). `TreeSet` can’t unless comparator handles nulls.

**Q115. Array covariance danger:**

```java
Number[] arr = new Integer[1]; arr[0] = 1.5; // ?
```

**A.** `ArrayStoreException` at runtime.

**Q116. `BigDecimal` scale pitfalls?**
**A.** `new BigDecimal(0.1)` is imprecise; use `BigDecimal.valueOf(0.1)` or string ctor; set `MathContext`/`RoundingMode` for divisions.

**Q117. `switch` on Strings—case sensitivity & null?**
**A.** Case‑sensitive; `null` throws NPE before matching.

**Q118. Order of field initialization with inheritance?**
**A.** Parent static → child static → parent instance → parent ctor → child instance → child ctor.

**Q119. `Collectors.toMap` duplicate keys?**
**A.** Throws `IllegalStateException` unless a merge function is provided.

**Q120. `Objects.hash(a, b)` vs custom hash?**
**A.** Simpler but may allocate varargs array; for hot paths use custom 31‑based multiplication.
